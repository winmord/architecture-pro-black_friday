# 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования

## Задание 10.1: Определение критически важных данных для миграции

### Анализ сущностей

| Сущность                 | Объём данных  | Частота операций                 | Требования к консистентности    | Целесообразность миграции           |
|--------------------------|---------------|----------------------------------|---------------------------------|-------------------------------------|
| **Заказы (orders)**      | Высокий       | Высокая (50K запросов/сек в пик) | Высокая (финансовые транзакции) | **Критично**                        |
| **Товары (products)**    | Средний       | Очень высокая (каталог, остатки) | Средняя (остатки критичны)      | **Критично**                        |
| **Корзины (carts)**      | Высокий       | Экстремально высокая             | Высокая (пользовательский опыт) | **Критично**                        |
| **История заказов**      | Очень высокий | Средняя                          | Низкая                          | Частично (можно оставить в MongoDB) |
| **Сессии пользователей** | Высокий       | Экстремально высокая             | Средняя                         | **Критично**                        |

### Обоснование выбора Cassandra

**Cassandra подходит для:**

1. **Заказы (orders)** — высокая скорость записи, геораспределённость, отказоустойчивость
2. **Товары (products)** — высокая нагрузка на чтение, обновление остатков, горизонтальное масштабирование
3. **Корзины (carts)** — экстремально высокая нагрузка, низкая задержка, временные данные
4. **Сессии** — высокая частота чтения/записи, TTL, распределённая нагрузка

**Оставляем в MongoDB:**

- **История заказов** — аналитические запросы, сложные агрегации, Cassandra не оптимизирована для OLAP
- **Категории товаров** — иерархические данные, редкие обновления

## Задание 10.2: Концептуальная модель данных

### 1. Таблица `orders` (Заказы)

```sql
CREATE TABLE orders (
    -- Partition Key: клиент + месяц (равномерное распределение)
    client_month text,           -- формат: "user123_2024-01"
    
    -- Clustering Columns (сортировка внутри партиции)
    order_id uuid,               -- уникальный ID заказа
    order_date timestamp,        -- дата заказа (сортировка)
    
    -- Данные заказа
    status text,                 -- статус заказа
    total_amount decimal,        -- общая сумма
    geozone text,                -- геозона доставки
    items text,                  -- JSON с товарами (или отдельная таблица)
    
    PRIMARY KEY (client_month, order_id, order_date)
) WITH CLUSTERING ORDER BY (order_id DESC, order_date DESC);
```

**Обоснование:**

- **Partition key**: `client_month` — равномерное распределение по пользователям и месяцам, предотвращает "горячие"
  партиции
- **Кластерные ключи**: `order_id` + `order_date` — обеспечивают уникальность и сортировку
- **Преимущества**:
    - Заказы одного пользователя распределены по месяцам (нет гигантской партиции)
    - Быстрый поиск заказов пользователя за конкретный месяц
    - Добавление новых узлов не требует перераспределения данных (hash-based)

### 2. Таблица `products` (Товары и остатки)

```sql
-- Таблица товаров (каталог)
CREATE TABLE products (
    -- Partition Key: категория (для равномерного распределения)
    category text,
    
    -- Clustering Keys
    product_id uuid,
    popularity_tier int,         -- искусственное поле для дробления горячих категорий
    
    -- Данные товара
    name text,
    price decimal,
    attributes text,             -- JSON с цветом, размером и т.д.
    created_at timestamp,
    
    PRIMARY KEY ((category, popularity_tier), product_id)
);

-- Таблица остатков (высокочастотные обновления)
CREATE TABLE product_stock (
    -- Partition Key: геозона (локальность данных)
    geozone text,
    
    -- Clustering Keys
    product_id uuid,
    warehouse_id text,           -- ID склада (для детализации)
    
    -- Данные остатков
    quantity int,
    last_updated timestamp,
    
    PRIMARY KEY (geozone, product_id, warehouse_id)
);
```

**Обоснование:**

- **Products**: `category` + `popularity_tier` — разбивает горячую категорию "Электроника" на 10 частей
- **Product_stock**: `geozone` — запросы остатков всегда идут по геозоне (Москва, Екатеринбург и т.д.)
- **Преимущества**:
    - Равномерное распределение даже для популярных категорий
    - Обновления остатков идут в конкретную партицию (одна геозона)
    - Нет перераспределения данных при масштабировании

### 3. Таблица `carts` (Корзины)

```sql
CREATE TABLE carts (
    -- Partition Key: user_id или session_id
    partition_key text,          -- "user:123" или "session:abc123"
    
    -- Clustering Key
    cart_id uuid,                -- уникальный ID корзины
    
    -- Данные корзины
    items text,                  -- JSON с товарами
    status text,                 -- active, ordered, abandoned
    created_at timestamp,
    updated_at timestamp,
    expires_at timestamp,        -- для TTL
    
    PRIMARY KEY (partition_key, cart_id)
) WITH default_time_to_live = 604800;  -- автоматическое удаление через 7 дней
```

**Обоснование:**

- **Partition key**: `partition_key` (user или session) — все данные корзины в одной партиции
- **TTL**: автоматическая очистка заброшенных корзин
- **Преимущества**:
    - Быстрое чтение/запись активной корзины
    - Простое слияние гостевой и пользовательской корзин
    - Равномерное распределение за счёт хеширования ключей

### 4. Таблица `sessions` (Сессии)

```sql
CREATE TABLE sessions (
    -- Partition Key: session_id
    session_id text,
    
    -- Clustering Key
    token_hash text,             -- хеш токена для быстрого поиска
    
    -- Данные сессии
    user_id text,                -- ID пользователя (если авторизован)
    user_agent text,
    ip_address text,
    created_at timestamp,
    expires_at timestamp,
    session_data text,           -- JSON с данными сессии
    
    PRIMARY KEY (session_id, token_hash)
) WITH default_time_to_live = 86400;  -- 24 часа
```

**Обоснование:**

- **Partition key**: `session_id` — быстрый доступ к сессии по ID
- **TTL**: автоматическая очистка истекших сессий
- **Преимущества**:
    - Экстремально высокая скорость чтения (одна партиция)
    - Автоматическая очистка старых данных
    - Равномерное распределение по кластеру

## Задание 10.3: Стратегии обеспечения целостности данных

### Сравнение стратегий

| Стратегия               | Принцип работы                                 | Latency | Гарантии      | Когда использовать                   |
|-------------------------|------------------------------------------------|---------|---------------|--------------------------------------|
| **Hinted Handoff**      | Временное хранение записей на недоступном узле | Низкая  | Слабая        | Временные данные (корзины, сессии)   |
| **Read Repair**         | Проверка консистентности при чтении            | Средняя | Сильная       | Критические данные (заказы, остатки) |
| **Anti-Entropy Repair** | Периодическая фоновая сверка                   | Высокая | Очень сильная | Все данные (регулярно)               |

### Распределение по сущностям

#### 1. Заказы (orders) — критически важные

```yaml
Стратегии:
  - Read Repair: ВКЛЮЧЕН (вероятность 0.1)
  - Hinted Handoff: ВКЛЮЧЕН (ограниченный, 3 часа)
  - Anti-Entropy Repair: ЕЖЕДНЕВНО (в 2:00)

Консистентность: QUORUM на чтение и запись
```

**Обоснование**:

- Нельзя потерять заказ (финансы)
- Read Repair обеспечивает консистентность при чтении
- Ежедневный repair для долгосрочной согласованности

#### 2. Товары и остатки (products) — высокая частота обновлений

```yaml
Стратегии:
  - Read Repair: ВКЛЮЧЕН (вероятность 0.05)
  - Hinted Handoff: ВЫКЛЮЧЕН (остатки должны быть точными)
  - Anti-Entropy Repair: ЕЖЕНЕДЕЛЬНО

Консистентность:
  - Чтение остатков: QUORUM
  - Обновление остатков: QUORUM
  - Чтение каталога: ONE
```

**Обоснование**:

- Остатки требуют высокой точности (overselling недопустим)
- Hinted Handoff может привести к рассинхронизации
- Read Repair с низкой вероятностью не увеличивает latency сильно

#### 3. Корзины (carts) — временные данные

```yaml
Стратегии:
  - Read Repair: ВЫКЛЮЧЕН
  - Hinted Handoff: ВКЛЮЧЕН (максимум 1 час)
  - Anti-Entropy Repair: НЕ ТРЕБУЕТСЯ (TTL)

Консистенность: ONE (чтение и запись)
```

**Обоснование**:

- Корзины временные (TTL), потеря не критична
- Hinted Handoff обеспечивает доступность при отказе узлов
- Высокая скорость важнее абсолютной консистентности

#### 4. Сессии (sessions) — высокая доступность

```yaml
Стратегии:
  - Read Repair: ВЫКЛЮЧЕН
  - Hinted Handoff: ВКЛЮЧЕН (3 часа)
  - Anti-Entropy Repair: ЕЖЕНЕДЕЛЬНО

Консистенность: ONE (чтение и запись)
```

**Обоснование**:

- Высокая скорость критична для пользовательского опыта
- Временная несогласованность сессий некритична (пользователь перелогинится)
- Hinted Handoff повышает доступность
